# Professional QA Report Specification

**Version:** 1.0  
**Date:** July 18, 2026  
**Purpose:** Define the structure, styling, and AI generation guidelines for enterprise-grade QA reports  
**Design Philosophy:** Reports should read as if written by a human QA Lead, not generated from execution logs

---

## 1. Design Philosophy

### 1.1 Core Principles

1. **Business-First Language**: Use terminology that stakeholders understand (validations, checkpoints, business rules)
2. **Semantic Grouping**: Group actions by business intent, not chronological execution
3. **Observation-Driven**: Each validation includes AI-generated observations of actual system state
4. **Evidence-Based**: Screenshots are evidence, not random captures
5. **Professional Aesthetics**: Enterprise-grade design with consistent typography and color coding

### 1.2 Terminology Changes

| Current Term | New Term | Rationale |
|--------------|----------|-----------|
| Step | Validation / Checkpoint | Focuses on what was validated, not what was executed |
| Action | Action Taken | Describes business action, not technical implementation |
| Expected | Observation | AI-generated observation of actual state |
| Actual | Result | Clear pass/fail/warning outcome |
| Timeline | Validation Summary | Checklist of what was validated |

## 3. Sections and Ordering

### 3.1 Section 1: Report Header

**Purpose:** Immediate status identification and metadata

**Elements:**
- Status Badge (large, prominent)
- Report Title
- Execution ID
- Scenario Name
- Metadata Grid (4 columns)

**Order:**
1. Status Badge (top-left)
2. Report Title (top-right)
3. Execution ID (below title)
4. Scenario Name (below execution ID)
5. Metadata Grid (below scenario)

### 3.2 Section 2: Executive Summary

**Purpose:** Business-focused summary for stakeholders

**Elements:**
- Overall Result (PASS/FAIL)
- Business workflow summary
- Key achievements
- Critical issues (if any)
- Recommendations (if issues)
- Business rule compliance

**Order:**
1. Overall Result (large badge)
2. Business workflow summary (paragraph)
3. Key achievements (bullet list)
4. Critical issues (bullet list, if any)
5. Recommendations (bullet list, if issues)
6. Business rule compliance (table or list)

### 3.3 Section 3: Validation Summary

**Purpose:** Quick checklist of all validations

**Elements:**
- Validation count (e.g., "8 Validations")
- Checklist with status indicators
- Grouped by business phase (optional)

**Order:**
1. Validation count header
2. Checklist (vertical list with checkmarks/crosses)

**Example:**
```
VALIDATION SUMMARY (8 Validations)

✓ Booking Page Loaded
✓ Hotel Search Successful
✓ Hotel Selected
✓ Customer Details Accepted
✓ Payment Accepted
✓ Booking Created
✓ Order Number Generated
✓ Order Number Format Verified
```

### 3.4 Section 4: Business Rule Validation

**Purpose:** Explicit validation of business rules with status indicators

**Elements:**
- Business rule name
- Compliance status (✅/❌)
- Confidence score (optional)
- Reasoning (optional)

**Order:**
1. Section header
2. Business rule table or list

**Example:**
```
BUSINESS RULE VALIDATION

Business Rule                    Status    Confidence
────────────────────────────────────────────────────
Order number generated            ✅        98%
Order number length = 10          ✅        95%
Uppercase alphanumeric           ✅        100%
Booking completed                ✅        99%
Payment processed                ✅        97%
Confirmation displayed           ✅        96%
```

### 3.5 Section 5: Validation Details

**Purpose:** Detailed evidence for each validation

**Elements per Validation:**
- Validation Number and Title
- Observation (AI-generated from DOM state, assertions, timeline)
- Confidence Score (0-100%)
- Confidence Reasoning
- Result (PASS/FAIL/WARNING/INFO)
- Action Taken (business description)
- Evidence (Screenshot reference)

**Order:**
1. Validation Number and Title
2. Observation
3. Confidence Score + Reasoning
4. Result
5. Action Taken
6. Evidence (reference to Evidence Index)

### 3.6 Section 6: Evidence Index

**Purpose:** Centralized catalog of all screenshots

**Elements:**
- Screenshot number
- Screenshot description
- Related validation(s)
- Thumbnail (optional)

**Order:**
1. Section header
2. Screenshot list with references

**Example:**
```
EVIDENCE INDEX

Screenshot 1: Booking Page Loaded
  Related: Validation 1
  [Thumbnail]

Screenshot 2: Hotel Search Results
  Related: Validation 2
  [Thumbnail]

Screenshot 3: Hotel Selection
  Related: Validation 3
  [Thumbnail]

Screenshot 4: Customer Details Form
  Related: Validation 4
  [Thumbnail]

Screenshot 5: Payment Processing
  Related: Validation 5
  [Thumbnail]

Screenshot 6: Booking Confirmation
  Related: Validation 6
  [Thumbnail]

Screenshot 7: Order Number Display
  Related: Validation 7
  [Thumbnail]

Screenshot 8: Final Booking State
  Related: Validation 8
  [Thumbnail]
```

### 3.7 Section 7: Footer

**Purpose:** Attribution and timestamp

**Elements:**
- Platform attribution
- Generation timestamp
- Report version

## 4. Typography and Styling

### 4.1 Font Family

**Primary:** Inter, Roboto, or system-ui (modern sans-serif)

**Hierarchy:**
- **H1 (Report Title):** 28px, bold, #1e293b
- **H2 (Section Headers):** 20px, semibold, #334155
- **H3 (Validation Titles):** 16px, semibold, #475569
- **Body Text:** 14px, regular, #64748b
- **Metadata:** 12px, medium, #94a3b8
- **Code/Monospace:** 13px, JetBrains Mono or Consolas

```
You are an expert QA Lead writing an executive summary for stakeholders.

Test Case: {test_case_title}
Expected Result: {expected_result}

Validation Results:
{validation_results_summary}

Business Rules:
{business_rules}

Execution Metrics:
- Total Validations: {total_validations}
- Passed: {passed_count}
- Failed: {failed_count}
- Warnings: {warning_count}
- Duration: {duration}

Generate an executive summary with:
1. A 2-3 sentence business workflow narrative
2. 3-4 bullet points for key achievements (if passed) or critical issues (if failed)

Tone: Professional, business-focused, concise
Audience: Non-technical stakeholders
Focus: Business outcomes, not technical implementation
```

## 8. Screenshot Placement

### 8.1 Evidence Section

**Purpose:** Provide visual evidence for each validation

**Placement:** Right side of validation card (desktop), bottom (mobile)

**Caption Format:** "Screenshot {number}" or "Evidence {number}"

**Naming Convention:**
- `validation-{nn}.png` (where nn is validation number)
- Fallback: `step-{nn}.png` (for backward compatibility)

**Selection Logic:**
1. Primary: Screenshot taken during validation
2. Fallback 1: Last screenshot before validation completion
3. Fallback 2: First screenshot after validation start
4. Fallback 3: No screenshot placeholder

## 12. AI Generation Guidelines

### 12.1 Single-Pass Validation Generation

**Philosophy:** Generate all validation data in a single LLM call to ensure consistency and reduce latency.

**Input Data:**
- Test case title and description
- Test case steps
- Expected result
- Playwright timeline events
- DOM state (page elements, URLs, assertions)
- Screenshots (as supporting evidence only)
- Business rules (if defined)

**Prompt Template:**
```
You are an expert QA Lead analyzing test execution results. Generate a professional validation report.

TEST CASE:
Title: {test_case_title}
Description: {test_case_description}
Expected Result: {expected_result}

TEST CASE STEPS:
{test_case_steps}

EXECUTION DATA:
Timeline Events: {timeline_events}
DOM State: {dom_state}
Page URLs: {page_urls}
Assertions: {assertions}
Screenshots: {screenshot_list}

BUSINESS RULES:
{business_rules}

For each test case step, generate a validation object with:

1. validation_title: Business-focused title (3-8 words)
   - Focus on what was validated, not what was executed
   - Use professional QA terminology
   - Example: "Navigate to booking page" → "Booking Page Loaded"

2. business_goal: What business objective this validation achieves

3. observations: 2-4 sentences describing actual system state
   - Analyze DOM state, assertions, timeline (NOT screenshots)
   - Screenshots corroborate but don't drive observations
   - Be factual and objective
   - Use professional QA terminology

4. confidence: Score 0-100% with reasoning
   - How confident are you in this observation?
   - Reasoning: What evidence supports this confidence?

5. result: One of PASS, FAIL, WARNING, INFO
   - PASS: Validation completed successfully
   - FAIL: Validation failed with error
   - WARNING: Completed but with concerns
   - INFO: Informational validation

6. action_taken: Business action description (1-2 sentences)
   - Describe what was accomplished, not technical implementation
   - Use professional terminology

7. evidence: Screenshot reference (e.g., "Screenshot 7")
   - Which screenshot best supports this validation?

8. business_rules: Array of business rule validations
   - rule: Business rule description
   - status: "✅" or "❌"
   - confidence: 0-100%
   - reasoning: Why this status

Output format: JSON array of validation objects

IMPORTANT:
- Generate exactly one validation per test case step
- Maintain consistency in terminology across all validations
- Use business language, not technical implementation details
- Screenshots are evidence, not the primary observation source
```

**Response Model:**
```python
class BusinessRuleValidation(BaseModel):
    rule: str = Field(description="Business rule description")
    status: str = Field(description="✅ or ❌")
    confidence: int = Field(description="0-100 confidence score")
    reasoning: str = Field(description="Why this status was assigned")

class Validation(BaseModel):
    validation_title: str = Field(description="Business-focused validation title")
    business_goal: str = Field(description="Business objective achieved")
    observations: str = Field(description="2-4 sentences describing actual state from DOM/assertions/timeline")
    confidence: int = Field(description="0-100% confidence in observation")
    reasoning: str = Field(description="Evidence supporting confidence score")
    result: str = Field(description="PASS, FAIL, WARNING, or INFO")
    action_taken: str = Field(description="Business action description")
    evidence: str = Field(description="Screenshot reference (e.g., 'Screenshot 7')")
    business_rules: list[BusinessRuleValidation] = Field(default_factory=list)

class ValidationList(BaseModel):
    validations: list[Validation]
```

### 12.2 Observation Source Priority

**Primary Sources (in order of priority):**
1. **DOM State** - Page elements, their properties, visibility
2. **Assertions** - Explicit validation checks performed
3. **Timeline** - Sequence of events and their outcomes
4. **Page URL** - Current page and navigation history

**Supporting Sources:**
- **Screenshots** - Visual corroboration only, not primary driver

**Rationale:**
- DOM state is objective and programmatically accessible
- Assertions are explicit validation intent
- Timeline provides execution context
- Screenshots are subjective and require OCR/vision analysis
- Screenshots should corroborate, not drive, observations

### 12.3 Confidence Scoring Guidelines

**Score Ranges:**
- **95-100%**: Strong evidence from DOM state, assertions, and timeline
- **85-94%**: Good evidence with minor ambiguity
- **70-84%**: Moderate evidence, some uncertainty
- **50-69%**: Limited evidence, significant uncertainty
- **Below 50%**: Insufficient evidence, observation should be marked as WARNING

**Confidence Factors:**
- DOM state clarity and completeness
- Assertion coverage
- Timeline consistency
- Screenshot corroboration
- Error message clarity

**Example Reasoning:**
```
Confidence: 98%
Reasoning: The page title, order number field, and booking confirmation controls
are clearly visible in the DOM state. All assertions passed. Timeline shows
sequential completion without errors. Screenshot corroborates the DOM state.
```

### 12.4 Business Rule Validation Guidelines

**Rule Extraction:**
- Extract from test case expected result
- Extract from test case description
- Extract from requirement documents (if available)
- Common business rules: format validation, presence checks, state transitions

**Validation Approach:**
- Check if rule is explicitly asserted in test
- Check if DOM state satisfies rule
- Check if timeline indicates rule compliance
- Assign confidence based on evidence strength

**Example:**
```
Rule: "Order number must be 10 characters"
Status: ✅
Confidence: 100%
Reasoning: Order number field in DOM shows exactly 10 characters.
Assertion explicitly validates length.
```

### 12.5 Executive Summary Generation

**Input Data:**
- All validation results
- Test case context
- Business rule compliance summary
- Execution metrics

**Prompt Template:**
```
You are a QA Lead writing an executive summary for stakeholders.

TEST CASE:
{test_case_title}
Expected Result: {expected_result}

VALIDATION SUMMARY:
{validation_summary}

BUSINESS RULE COMPLIANCE:
{business_rule_compliance}

EXECUTION METRICS:
- Total Validations: {total}
- Passed: {passed}
- Failed: {failed}
- Warnings: {warnings}
- Duration: {duration}

Generate an executive summary with:
1. Business workflow narrative (2-3 sentences)
2. Key achievements (3-4 bullets) if passed, OR critical issues (if failed)
3. Business rule compliance assessment
4. Recommendations (if issues exist)

Tone: Professional, business-focused
Audience: Non-technical stakeholders
Focus: Business outcomes, not technical implementation details

Output: JSON with narrative, achievements/issues, compliance, recommendations
```

**Response Model:**
```python
class ExecutiveSummary(BaseModel):
    narrative: str = Field(description="2-3 sentence business workflow summary")
    achievements: list[str] = Field(description="3-4 key achievements (if passed)")
    critical_issues: list[str] = Field(description="3-4 critical issues (if failed)")
    business_rule_compliance: str = Field(description="Compliance assessment")
    recommendations: list[str] = Field(description="1-2 actionable recommendations (if issues)")
```

## 14. Implementation Architecture

### 14.1 Proposed Agent Chain

```
Playwright Timeline
        ↓
Execution Analyzer Agent
        ↓
Professional Report Generator Agent
        ↓
HTML/PDF
```

### 14.2 Agent Responsibilities

**Execution Analyzer Agent**
- Analyzes Playwright timeline, DOM state, assertions, page URL
- Groups related actions by business intent
- Identifies business intents and validation points
- Removes duplicates and retry artifacts
- Maps to test case structure
- Generates validation titles
- Extracts observations from DOM state, assertions, timeline (screenshots as supporting evidence only)
- Determines validation results
- Generates action taken descriptions
- Validates business rules
- Assigns confidence scores with reasoning
- Produces structured validation objects

**Professional Report Generator Agent**
- Receives structured validation objects
- Orchestrates report generation
- Applies Jinja2 templates
- Generates HTML/PDF
- Ensures styling consistency
- Creates evidence index

### 14.3 Data Flow

```
ExecutionResult
    ↓
Execution Analyzer Agent
    ↓
StructuredValidationList
    {
      validation_title: string,
      business_goal: string,
      observations: string,
      result: "PASS" | "FAIL" | "WARNING" | "INFO",
      action_taken: string,
      evidence: string,  // Screenshot reference
      business_rules: [
        {
          rule: string,
          status: "✅" | "❌",
          confidence: number,
          reasoning: string
        }
      ],
      confidence: number,
      reasoning: string
    }
    ↓
Professional Report Generator Agent
    ↓
ReportContext
    {
      executive_summary: {...},
      validation_summary: [...],
      validation_details: [...],
      business_rule_validation: [...],
      evidence_index: [...]
    }
    ↓
Jinja2 Templates
    ↓
HTML/PDF
```
