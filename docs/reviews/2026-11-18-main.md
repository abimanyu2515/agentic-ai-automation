# Review, main (uncommitted), 2026-11-18

**Reviewed by**: Sonnet 5.5 (author on a different model)
**Scope**: 66 tracked files changed, 35 untracked files read, uncommitted on main (rag_service.py deleted)
**Verdict**: Changes requested

## Summary
You added a per project agentic RAG layer: RAGFlow datasets per project, a background KnowledgeIndexer with retries and a startup sweep, knowledge entry hooks, a search_knowledge chat tool, a graded retrieval agent, groundedness scoring, and a retrieval eval script. The design follows the spec closely, the new knowledge routes use real auth and ownership checks, and the tests are broad. The headline problems are that several mutating routes still have no auth while this change gives them new destructive or data leaking side effects, that the default JSON store is now written from a second thread while most writers take no lock, and that remote RAGFlow cleanup is lost when RAGFlow is down or the server restarts.

## Major
### 🟠 Unauthenticated mutating routes now do more damage, `backend/main.py:1576`
**Problem**: These routes have no `get_current_user`, `has_permission` or `require_project_access`: test case PUT (1576) and DELETE (1596), `delete_failed_executions` (1609), `delete_execution` (1625), `PUT /api/v1/settings` (1740), and `DELETE /api/v1/projects/{project_id}` (1766). Confirmed from the code. The test case routes also never check that the test case belongs to the `project_id` in the URL. Most of this is older, but your change adds new side effects to it. `delete_project` now removes the project's uploaded files from disk and queues deletion of its RAGFlow dataset. `save_settings` now writes a new RAGFlow API key into the process environment, and it still accepts `ragflow_api_base`. Anyone who can reach the server can point the base URL at their own host. After that, every upload, every search and the bearer key go to that host.
**Why it matters**: An anonymous caller can delete a project's knowledge, or redirect RAGFlow traffic and capture the key and your project documents.
**Suggested fix**: Add the same user, permission and project access dependencies you used on the knowledge routes to these routes, starting with `delete_project`, `save_settings` and the test case and execution routes. Check that the test case belongs to the project. Consider refusing a changed `ragflow_api_base` unless the caller is an admin.

### 🟠 JSON store is written from the indexer thread without a lock on most writers, `backend/repository/project_repository.py:299`
**Problem**: `_write_lock` is taken only by `create_project`, `update_project`, and the new document, entry and dataset methods (lines 383, 419, 795 to 866). Other writers such as `save_test_cases`, `save_execution_result`, and the scenario and requirement saves do a plain read, change, write of the whole file with no lock. The indexer thread now writes documents and entries to the same file while request threads write. The `.tmp` file name is also shared.
**Why it matters**: JSON is the default store. A knowledge write that lands between another writer's read and write silently loses either the knowledge update or the test case or execution update.
**Suggested fix**: Take `_write_lock` in every JSON read, change, write method, or route all writes through one helper that holds it. Add a test that runs two writer threads against one store.

### 🟠 Remote RAGFlow cleanup is lost when RAGFlow is down or the server restarts, `backend/services/knowledge_indexer.py:514`
**Problem**: Remote document deletes and dataset deletes are in memory jobs. They retry only on the configured delays (10, 60, 300 seconds), then `_delete_remote` (514) and `_delete_dataset` (523) only log a warning. Nothing is stored and nothing retries after a restart. The startup sweep only looks at documents, not leftover deletes. Confirmed: a project deleted while RAGFlow is down leaves its dataset behind, and a failed document delete leaves its remote document.
**Why it matters**: Deleted project data stays in RAGFlow, which is a storage and data retention problem, and the project's dataset can never be found again from the app.
**Suggested fix**: Persist pending remote deletes (a small table or a field on the project), retry them in the startup sweep, and show them in the knowledge status. The reindex script could also report datasets that no live project owns.

## Minor
### 🟡 Groundedness call uses the 30 second default timeout, `backend/agents/evaluation_agent.py:236`
**Problem**: `structured_generate` defaults to `timeout=30` (`backend/services/llm.py:710`). The groundedness prompt holds the whole retrieved context plus every test case, so it is the largest call in the stage. The retrieval grader passes `timeout=60` for a smaller prompt. A timeout is caught and logged, which leaves `groundedness_score` null.
**Why it matters**: This is the likely reason scores are often null, so the feature looks broken.
**Suggested fix**: Pass a larger explicit timeout, ideally from settings (`llm.timeout` is 60 and is not used here), and put the timeout cause in the stage log.

### 🟡 A document that times out or fails parsing keeps its remote copy, `backend/services/knowledge_indexer.py:374`
**Problem**: On `PARSE_TIMED_OUT` (and on a parse failure at line 372) the local document is marked failed, but the remote document stays in RAGFlow, still parsing or half parsed. Confirmed. A retry upload then creates a second remote document.
**Suggested fix**: Queue a remote delete (the delete path already stops a parse) before marking the document failed. The timeout test at `backend/tests/test_knowledge_base.py:145` should assert it.

### 🟡 Entry is marked indexed before RAGFlow finishes parsing, `backend/services/knowledge_indexer.py:452`
**Problem**: Source entries are saved as `indexed` right after upload. No poll watches their parse. If parsing fails or is slow, the entry shows indexed but is not searchable, and the hash check at line 432 skips every later attempt.
**Suggested fix**: Poll entry parses like documents, or do not skip on hash until a parse has completed.

### 🟡 Duplicate passages in search and feature_mapping, `backend/services/knowledge_service.py:272`
**Problem**: `search` filters and sorts but never removes repeated text. The same file uploaded twice, or overlapping chunks, appear several times. `FeatureInventoryAgent` joins the top 3 raw items (`backend/agents/feature_inventory_agent.py:112`) and saves them, and the retrieval agent only de-duplicates by `chunk_id` (`knowledge_retrieval_agent.py:258`). Confirmed.
**Suggested fix**: Drop items whose normalized text already appeared, before applying `top_k`. Consider reusing an upload that has the same content hash.

### 🟡 Token Utilization labels the retrieval stage "Other", `backend/services/token_usage_service.py:36`
**Problem**: `AGENT_STAGES` has no entry for `knowledge_retrieval_agent` (the name used at `knowledge_retrieval_agent.py:65`), so `stage_for` returns "Other". The mapping lives in the backend, not the frontend. The chat and feature inventory agents are missing too.
**Suggested fix**: Add `"knowledge_retrieval_agent": "Retrieval"` and the other missing agents.

### 🟡 `hashchange` listener registered only after startup awaits, `frontend/js/app.js:4399`
**Problem**: `initAuth` awaits permissions, settings, `loadProjects` and `selectProject` (lines 4373 to 4392) before it adds the listener. A nav click in that window changes the hash and is never routed. Confirmed. Each re-login also calls `initAuth` again, which adds another listener.
**Suggested fix**: Register the listener once, early, guarded by a flag.

### 🟡 Jira webhook scans every project on every call, `backend/main.py:3190`
**Problem**: For each webhook the code lists all projects and, per project, loads all executions and test cases (`project_defect_keys`) before the status filter runs. The webhook has no auth.
**Suggested fix**: Look up the key once (an index from key to projects, or one repository query) and keep the cheap status filter first where it does not change behavior.

### 🟡 Deleting a scenario leaves stale test case entries, `backend/main.py:1447`
**Problem**: `delete_scenario` soft deletes child test cases (JSON store) but queues no knowledge removal. Their `test_case` entries and remote documents stay searchable until some other job touches them.
**Suggested fix**: Queue `remove=True` for the child test cases, like `delete_test_case` and the chat delete do.

### 🟡 Index declared in the migration but not in the model, `backend/database/db_models.py:273`
**Problem**: `ix_documents_project_remote_doc` is created in `f2b6c8d41a07` but `DocumentDB` has no matching `Index`. An autogenerate run would propose dropping it, and fresh `create_all` setups lack it.
**Suggested fix**: Add the index to `DocumentDB.__table_args__`.

### 🟡 Generated session file is untracked but not ignored, `.gitignore:33`
**Problem**: `backend/playwright/artifacts/BATCH-20261117-656/storage_state.json` is a generated artifact written by `batch_queue_manager.py:76`. `.gitignore` only covers `backend/playwrightt/artifacts/` (two t), a different folder. The file here has no cookies and no origins, so nothing secret is in it today. A real batch writes cookies there, and the file is removed only on some recovery paths.
**Suggested fix**: Do not commit it. Add `backend/playwright/artifacts/` to `.gitignore`.

## Strengths
- The retrieval contract only takes a `Project`, never a raw dataset ID, and search maps every chunk back to a local record of the same project. That makes cross project leaks hard.
- The indexer design is careful: IDs only in the queue, timed jobs instead of sleeps, a write guard so a save cannot revive a deleted document, and one dataset per project under a lock.
- The new knowledge routes check auth, permission and project access before lookup, and the tests cover outsiders, stakeholders and cross project documents.
- Retrieval never fails the workflow, fences chunk text as data, and the graph takes injected agents so tests need no live LLM.
- The five Alembic revisions form one linear chain with one head, and they are additive or nullable.
- The two recent fixes hold: `resolve_project_response(p, all_projects=None)` treats an empty list as loaded, and the `text(...)` index predicates are covered by `test_db_models.py`.
