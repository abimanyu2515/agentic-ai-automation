## Summary

This change bounds the scenario generation path so a stuck LLM surfaces as an error instead of a forever spinner. Backend validation fails fast on a missing key or base, every litellm call gets a 60 second cap, and the frontend aborts at 120 seconds with a friendly note. The direction is sound, but the frontend timeout check looks for the wrong error name, the backend worst case run time still exceeds the frontend abort, and the new validation logic has no tests.

## Major

### 🟠 Timeout check misses the real error name, `frontend/js/api.js:124`

**Problem**: `AbortSignal.timeout()` aborts with a `TimeoutError` DOMException in current browsers, so `fetch` rejects with `name === 'TimeoutError'`, not `'AbortError'`. The catch only handles `'AbortError'`, so the friendly guidance message never shows on a real timeout.

**Why it matters**: The user still gets an alert (spinner clears, core fix holds), but with the raw text "The operation timed out" and none of the intended guidance about LLM settings. The main message this change was meant to deliver is dead code in practice.

**Suggested fix**: Accept both names in the check, then keep the rest of the path as is.

### 🟠 Backend worst case exceeds the frontend abort, `backend/services/llm.py:160` and `frontend/js/api.js:255`

**Problem**: `structured_generate` retries up to 3 times with a 60 second cap per call, so one request can run about 180 seconds. The frontend aborts at 120 seconds. On a slow but working LLM the user sees a timeout while the backend keeps running and later saves scenarios the user never saw.

**Why it matters**: A retry after such a timeout can duplicate scenarios in append mode, or wipe and redo a finished run in replace mode. The two budgets disagree by a full minute.

**Suggested fix**: Line the budgets up (lower the per call cap or the retry count, or raise the frontend abort so it sits above the backend worst case) and tell the user to refresh the list before retrying.

### 🟠 New validation logic has no test cover, `backend/services/llm.py:122`

**Problem**: `_require_valid_config` adds new branching error handling (cloud key check, ollama base check) with no unit test beside it.

**Why it matters**: The repo runs pytest with stub doubles, so this is cheap to cover, and a silent regression here reintroduces the exact hang this change removes.

**Suggested fix**: Ask `/test` for focused unit tests: missing key raises, ollama missing base raises, valid config passes, timeout reaches the completion call.

## Minor

### 🟡 Scenario wording lives in the shared request helper, `frontend/js/api.js:124`

**Problem**: `request()` serves every API call, but the timeout message names scenario generation. Accurate today (only `generateScenarios` passes a signal), wrong for any future caller that adds one.

**Why it matters**: Small confusion risk that grows as the pattern spreads.

**Suggested fix**: Keep a generic timeout message in `request()` and add the scenario specific guidance at the call site.

### 🟡 Setup failure returns HTTP 500, `backend/main.py:1371`

**Problem**: A missing key or base is a setup problem, but the route maps every `Exception` to 500 with "Scenario generation failed". The message reaches the user fine; the status tells monitors a server bug happened.

**Why it matters**: Noisy alerting and a misleading contract for API consumers.

**Suggested fix**: Map `LLMServiceError` from config validation to a 4xx or 502 class in this route.

### 🟡 Unknown provider skips validation, `backend/services/llm.py:125`

**Problem**: A provider string outside the known sets (including a typo) passes validation untouched and fails only after the 60 second cap.

**Why it matters**: Typos stay slow and confusing instead of fast and clear.

**Suggested fix**: Warn or fail on unrecognized provider values.

### 🟡 Sync route still holds the worker, `backend/main.py:1371`

**Problem**: The route stays synchronous, so one slow generation holds a uvicorn worker for the full run (up to about 180 seconds worst case) and stalls other requests on a single worker setup.

**Why it matters**: Tolerable for an internal tool and far better than forever, but the durable answer stays a background job with polling.

**Suggested fix**: Keep as a noted follow up, no action needed for this merge.

## Nits

- The timeout is a named overridable parameter, so the existing `**kwargs` pass through used by tests (`mock_response`) keeps working.
