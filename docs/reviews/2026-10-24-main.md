**Verdict**: Changes requested

## Summary
This change implements a major feature set around "project-specific testing" — introducing project-scoped configuration snapshots, live application reconnaissance via Playwright, deterministic script generation with validation, workspace token authentication, and Next.js proxy routes. The spec (docs/specs/0001-project-specific-testing/index.md) is comprehensive and well-structured. However, the implementation has several significant correctness and security gaps: URL normalization is inconsistent between validation and runtime, the ApplicationReconnaissanceAgent performs auto-login with hardcoded selectors (violating the "derive from test case" principle), credential handling in playwright_agent.py may leak credentials into LLM prompts via dom_context, the supervisor_agent.py routing for GENERATE_PLAYWRIGHT now routes to application_reconnaissance_agent but the workflow edge doesn't enforce project readiness before inspection, and test coverage for the new reconnaissance and validation logic is minimal.

## Blockers
### 🔴 ApplicationReconnaissanceAgent auto-login uses hardcoded selectors, violates agent contract
`backend/agents/application_reconnaissance_agent.py:386-458`
**Problem**: The `_perform_login` method hardcodes username/password field selectors (`input[name="username"]`, `input[name="password"]`, etc.) and submit button selectors (`button:has-text("Login")`). This directly violates the agent contract in AGENTS.md ("Derive every locator and value from the test case inputs") and the spec AC-13 ("Inspection uses the selected project's target URL and captured VaultService credentials... does not navigate to absolute URLs supplied by page hints"). The agent should only follow approved test case steps, not invent its own login flow.
**Why it matters**: In production, this will fail on any application that doesn't use these exact selectors, or worse — it will perform unauthorized state-changing actions (login) not specified in approved test cases, violating AC-18 ("Inspection may perform every action in the approved test case... It performs no unapproved action").
**Suggested fix**: Remove the auto-login logic entirely. Inspection should only navigate to URLs derived from approved test case steps/preconditions. If a test case requires login, its steps must explicitly include login actions, and the agent should use the inspected DOM context to find the correct selectors — not hardcoded fallbacks.

### 🔴 URL normalization rejects queries/fragments at validation but runtime uses full URL with path
`backend/services/project_configuration.py:56-97` vs `backend/agents/application_reconnaissance_agent.py:116-122`
**Problem**: `normalize_target_url` rejects URLs with query strings or fragments (line 63), but `ApplicationReconnaissanceAgent._reconnoiter` passes the stored `target_url` (which may have had path preserved) to Playwright's `page.goto()`. The spec says "URL normalization... preserves path encoding. Query strings, fragments, and userinfo are rejected" but the stored normalized URL still contains the path. However, the project creation in `main.py:388` calls `normalize_target_url` which strips query/fragment but *keeps path*. This is internally consistent but the `_safe_origin` method (line 262) strips the path for origin comparison, meaning navigation could go to different paths on the same origin. The spec AC-19 says "Additional origins come only from the selected project configuration. A page hint cannot add an origin or override project credentials."
**Why it matters**: If a project is created with `https://app.example.com/login?redirect=dashboard`, the query is rejected at creation (good), but if the stored URL is `https://app.example.com/login` and a test case step says "navigate to /dashboard", the agent may navigate outside the intended path. More critically, the origin enforcement in `_reconnoiter` (line 192) uses `_safe_origin` which compares only scheme+host+port, allowing navigation to any path on that origin — this may be intentional per spec, but the validation message "Target URL must be an absolute URL without credentials, queries, or fragments" is misleading since path is allowed.
**Suggested fix**: Update the validation error message to clarify that paths are allowed but query/fragment/userinfo are not. Ensure the stored normalized URL is used consistently as the base for all navigation, and that page hints (relative paths) are resolved against this base.

### 🔴 playwright_agent.py may leak credentials via dom_context to LLM
`backend/agents/playwright_agent.py:379-570`, `backend/agents/playwright_agent.py:424-429`
**Problem**: The `_generate_script` method receives `dom_context` which is populated by `ApplicationReconnaissanceAgent` from live inspection. The dom_context includes form fields with `name`, `id`, `placeholder`, `label` — but the inspection agent's `_extract_field_info` (line 498-553) does not filter out password fields. If a login form is inspected, the password field's `name="password"` and `type="password"` will be in dom_context. This dom_context is then passed to the LLM in the prompt (line 520). While the system prompt says "never hardcode credentials", the LLM sees the field structure including password field names.
**Why it matters**: The LLM could potentially use the password field name/selector in generated code. The test `test_script_generation_never_sends_project_credentials_to_llm` only checks that `target_username`/`target_password` values aren't in the prompt, not that dom_context doesn't contain credential field metadata.
**Suggested fix**: In `ApplicationReconnaissanceAgent._extract_field_info`, exclude fields with `type="password"` from the dom_context, or sanitize them to only include the selector without the field type/name. Add a test that verifies password field metadata doesn't reach the LLM.

### 🔴 Workflow graph routes GENERATE_PLAYWRIGHT to application_reconnaissance_agent without project readiness check
`backend/graph/workflow.py:342`, `backend/agents/supervisor_agent.py:156-164`
**Problem**: The supervisor's `route_start` for `GENERATE_PLAYWRIGHT` checks for approved test cases (line 160-163) but does NOT check project readiness (target_url, framework). The `ApplicationReconnaissanceAgent.run` does check for target_url (line 109-113) and raises `ApplicationInspectionError`, but this happens *after* the workflow has started. The spec AC-8 requires "Target URL, framework, and allowed origin updates are rejected while a related generation, batch, or execution operation is active" and AC-3 requires readiness before generation.
**Why it matters**: An operation can be queued for a project that isn't ready, wasting resources and producing a confusing error later in the pipeline. The project readiness check should be a precondition gate in the supervisor, not a runtime failure in the agent.
**Suggested fix**: Add `require_ready_project` check in `SupervisorAgent.route_start` for `GENERATE_PLAYWRIGHT` operation, similar to how `generate_playwright_script` in `workflow_service.py:416` does it.

## Major
### 🟠 ApplicationReconnaissanceAgent request routing blocks cross-origin but allows same-origin redirects that may escape path
`backend/agents/application_reconnaissance_agent.py:213-221`
**Problem**: The `restrict_requests` function only checks origin (`_safe_origin`) and link-local IPs. It allows any request to the same origin, including redirects to different paths, subdomains (if same origin), or even logout URLs. The spec AC-19 says "Browser redirects and requests are limited to the target origin and the project's explicit allowed_origins. Playwright request routing validates every destination origin." But the implementation doesn't validate the *path* — only the origin.
**Why it matters**: An application could redirect from `/login` to `/admin/delete-all` on the same origin, and the inspection would follow it. This violates the principle that inspection should only follow approved test case steps.
**Suggested fix**: Add path allowlisting based on URLs derived from approved test case steps. Reject any navigation to paths not explicitly referenced in the test case steps/preconditions.

### 🟠 playwright_agent.py test_data_template mode has race condition in marker validation
`backend/agents/playwright_agent.py:247-280`
**Problem**: The template generation retries once if markers are missing (line 251-271), but the retry uses `template_feedback` that lists missing markers. If the LLM *still* omits markers on the second attempt, it raises `ValueError` (line 277-280). However, the `markers` dict is built from the *first* test case's `test_data` keys (line 351-354), but the validation at line 282-287 checks that *all* approved test cases have identical `test_data` fields. If they differ, it raises — but this check happens *after* template generation, not before. The template is generated from the first test case only.
**Why it matters**: If test cases have different test_data fields, the template generation succeeds for the first case but then fails the consistency check, leaving partial state. The error message "test-data fields differ" doesn't indicate which fields.
**Suggested fix**: Move the field consistency check (line 282-287) to before template generation. Also, the retry logic should have a max attempt constant rather than hardcoded "once".

### 🟠 Script validation uses TypeScript compiler but doesn't validate Playwright-specific patterns
`backend/services/playwright_script_validation.py:33-82`
**Problem**: `_compile_typescript` only checks that TypeScript compiles (`tsc --noEmit`). It doesn't verify Playwright Test patterns like `test(`, `expect(`, proper imports, or async test functions. The `_validate_locators` function checks locator uniqueness against dom_context but the regex patterns are fragile (e.g., `_ROLE_LOCATOR` at line 11-14 uses a complex regex that may not match all valid Playwright locator syntaxes).
**Why it matters**: A script could pass compilation but be semantically invalid for Playwright (e.g., missing `expect`, using `page.click` instead of `page.locator().click()`). The agent's `_looks_like_valid_code` (line 139) does a basic check for `test(` and `import`, but this is done *before* validation, not as part of it.
**Suggested fix**: Add Playwright-specific AST checks (e.g., using `ts-morph` or more robust regex) to verify required patterns. Integrate the `_looks_like_valid_code` checks into the validation function so they're part of the same gate.

### 🟠 supervisor_agent.py route_after_human_approval_2 returns application_reconnaissance_agent for non-GENERATE_TESTCASES ops
`backend/agents/supervisor_agent.py:233-239`
**Problem**: `route_after_human_approval_2` returns `"application_reconnaissance_agent"` for any operation other than `GENERATE_TESTCASES`. This includes operations like `GENERATE_PLAYWRIGHT` which should go there, but also potentially other operations that shouldn't. The routing map in `workflow.py` shows `human_approval_agent_2` is only reached after `evaluation_agent` in the test case generation flow.
**Why it matters**: If a new operation is added that routes through `human_approval_agent_2`, it would unexpectedly go to reconnaissance. The conditional should be explicit about which operations continue to playwright generation.
**Suggested fix**: Check for `WorkflowOperation.GENERATE_PLAYWRIGHT` explicitly, not just "not GENERATE_TESTCASES".

### 🟠 WorkflowService._generate_project_scripts catches ValueError but not ApplicationInspectionError
`backend/services/workflow_service.py:454-479`
**Problem**: `_generate_project_scripts` calls `ApplicationReconnaissanceAgent.run` (line 455) which can raise `ApplicationInspectionError` (a subclass of `ValueError`). The catch at line 456 catches `ValueError`, which works, but then at line 469 it calls `PlaywrightAgent.run` which can also raise `ValueError` (for validation failures). Both are caught and converted to `ScriptGenerationBlockedError`, but the `reason` for inspection errors uses `getattr(exc, "reason", "target_unreachable")` while script validation errors always use `"script_validation_failed"`. This loses the specific inspection failure reason (e.g., "authentication_failed" vs "insufficient_evidence").
**Why it matters**: The caller gets a generic "script_validation_failed" even when the root cause was inspection failure. The `missing_evidence` mapping at line 461-465 only handles three hardcoded reasons.
**Suggested fix**: Catch `ApplicationInspectionError` explicitly before `ValueError`, preserve its `reason` and `message`, and include them in the `ScriptGenerationBlockedError`.

### 🟠 LLMService.generate timeout default differs from config
`backend/services/llm.py:138-153`
**Problem**: The `generate` method uses `timeout=timeout or self.config.timeout` (line 147). The config default is 60 seconds (settings.py:35), but `PlaywrightAgent._generate_script` passes `timeout=120` (line 575). This is fine, but the `structured_generate` method (line 190) also uses `timeout or self.config.timeout` — however, the `playwright_agent.py` doesn't use `structured_generate` for script generation, it uses `generate`. The inconsistency is that `structured_generate` has its own retry logic with 1-second sleeps (line 276), while `generate` has no retries.
**Why it matters**: If `structured_generate` is used for any agent that needs longer timeout (like scenario generation with complex prompts), the 60s default may be too short, and the retry logic adds up to 3 minutes total. There's no way to configure per-agent timeouts via settings.
**Suggested fix**: Add per-agent timeout configuration in settings, or at minimum document that agents requiring longer calls must pass explicit timeout.

### 🟠 State.model `dom_context` is untyped dict, no schema validation
`backend/models/state.py:55`
**Problem**: `dom_context: dict | None = None` accepts any dict structure. The `ApplicationReconnaissanceAgent` produces a specific structure (pages with forms, elements, navigation, etc.), but there's no validation that the structure matches what `PlaywrightAgent` and `playwright_script_validation` expect. If the structure changes, validation will silently produce wrong results.
**Why it matters**: The `_validate_locators` function (line 85-166) assumes specific keys like `pages`, `forms`, `fields`, `elements`, `navigation`, `match_count`. If any are missing, it may produce false positives/negatives.
**Suggested fix**: Define a Pydantic model for `DOMContext` and use it in `WorkflowState`. Add validation in `ApplicationReconnaissanceAgent.run` before assigning to state.

### 🟡 ApplicationReconnaissanceAgent._derive_urls_from_test_cases uses simple regex for URL extraction
`backend/agents/application_reconnaissance_agent.py:315-333`
**Problem**: The regex `r'https?://[^\s\'"<>]+'` for full URLs and `r'(?:go to|navigate to|visit|open)\s+([/\w\-_.]+)'` for relative paths are simplistic. They won't catch URLs in markdown links `[text](url)`, URLs with special characters, or navigation hints like "go to the dashboard page". The relative path pattern only matches single path segments.
**Why it matters**: Test cases with complex navigation steps may not have their URLs extracted, leading to incomplete inspection coverage.
**Suggested fix**: Use a more robust URL extraction approach, or better yet, rely on the approved test case steps being explicit about navigation (as the spec suggests) and have the agent follow steps sequentially rather than pre-extracting URLs.

### 🟡 playwright_agent.py imports `os` inside `_generate_script` method
`backend/agents/playwright_agent.py:390`
**Problem**: `import os` at line 390 is inside the method rather than at module top. This is a minor style issue but violates Python conventions and makes the import harder to track.
**Why it matters**: Minor, but consistent with the project's convention of module-level imports.

### 🟡 workflow_service.py uses global `active_execution_events` dict without cleanup
`backend/services/workflow_service.py:503`
**Problem**: `active_execution_events = {}` is a module-level dict that accumulates execution events by test_case_id. There's no TTL or cleanup mechanism. In a long-running server, this will grow unbounded.
**Why it matters**: Memory leak over time. Each execution adds an entry that's never removed.
**Suggested fix**: Add cleanup after execution completes (in the `finally` block), or use a bounded cache like `cachetools.TTLCache`.

### 🟡 Settings override.yaml loading silently ignores errors
`backend/config/settings.py:151-162`
**Problem**: The override.yaml merge (line 151-162) has a bare `except Exception: pass` which silently ignores any YAML parsing errors, missing file, or merge conflicts. This makes debugging configuration issues difficult.
**Why it matters**: A malformed override.yaml will be silently ignored, leading to confusing behavior where expected overrides don't apply.
**Suggested fix**: At minimum, log a warning when override loading fails. Ideally, validate the override structure and raise a clear error.

### 🟡 VaultService migration in on_startup doesn't handle concurrent access
`backend/main.py:219-222`
**Problem**: `migrate_credentials_to_vault()` iterates all projects and updates them. If multiple API workers start simultaneously (common in production with gunicorn/uwsgi), they'll all run migration concurrently, potentially causing race conditions on the JSON file or vault.
**Why it matters**: Duplicate migrations, corrupted vault entries, or lost updates.
**Suggested fix**: Add a file-based lock or use the existing interprocess write lock from the repository for migration. Run migration only once per deployment (e.g., via a separate migration script).

### 🟡 Hardcoded "playwright" framework default in multiple places
`backend/services/project_configuration.py:162`, `backend/agents/playwright_agent.py:183`, `backend/agents/application_reconnaissance_agent.py:175`
**Problem**: The default framework "playwright" appears in at least 3 places. If the default changes, all must be updated.
**Why it matters**: Maintenance burden and inconsistency risk.
**Suggested fix**: Define `DEFAULT_FRAMEWORK = "playwright"` in `project_configuration.py` and import it everywhere.

## Strengths
- The specification (docs/specs/0001-project-specific-testing/index.md) is exceptionally detailed with clear acceptance criteria, data flow tables, security model, and test scenarios. This is a model spec.
- The agent contract centered on `WorkflowState` is well-maintained: each agent validates inputs, logs start/completion, and updates only owned fields.
- Dependency injection in `build_graph()` is properly implemented, enabling agent tests without live LLM/browser.
- The `ProjectConfigurationError` with structured error codes and field-level details is a good pattern for API consumers.
- Test files follow a consistent two-layer pattern (LLMService integration + agent logic with stubs).
